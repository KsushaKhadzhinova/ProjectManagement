## 1. Цель
Освоить процессы управления рисками по PMBOK на проекте NotaCode:
- идентификация рисков;
- качественная оценка (P × I);
- реестр и карта рисков;
- выбор стратегий реагирования;
- элементы количественного анализа.

## 2. Объект
NotaCode — веб-IDE «diagram as code»:
- **состав:** Web IDE (React), Gateway (Node.js), пять Python-сервисов, PostgreSQL, MongoDB, Redis, RabbitMQ;
- **ресурсы:** один исполнитель, бюджет 0 BYN;
- **сроки:** 13 спринтов до защиты 18.12.2026, критический путь ПЗ2 — 11 недель.

## 3. Идентификация (методы из лекции 4)
- **Анализ документации:** архитектура (C4, ADR), agile-plan, SRS (`E:\NotaCode\docs`).
- **Контрольные листы:** 10 рисков Боэма, 5 источников ДеМарко–Листера.
- **Анализ предположений:** допущения ПЗ1, раздел 1.5.
- **Анализ прошлых версий:** `legacy-audit.md` — 19 дефектов DiagramCode (XSS в SVG, ключ Gemini в бандле, три несовместимых синтаксиса DSL, потерянный функционал между ветками).

## 6. Реагирование (по убыванию значимости)

| № | Стратегия | Мероприятия |
|---|---|---|
| R1 | Снижение | Walking skeleton в S0, поэтапное подключение сервисов, перенос Could have в Post-MVP |
| R2 | Снижение | ЛР реализуется как компонент продукта; дорожка Expedite, WIP = 1 |
| R3 | Уклонение | Единый каталог нотаций в `packages/contracts`, генерация подсветки и шаблонов из него |
| R4 | Уклонение | Экранирование, DOMPurify, CSP |
| R5 | Снижение | TDD с первого спринта, моки портов, линтер-правило |
| R6 | Снижение | Обоснование стека в записке, согласование в S1 |
| R7 | Принятие | Буферный спринт S12, ADR и документация |
| R9 | Передача | Резервный провайдер Fly.io, локальный docker compose |
| R8 | Снижение | Несколько LLM-провайдеров, заглушка по умолчанию, Ollama |
| R11 | Принятие | Уточнение даты в S1, MoSCoW, перенос Should have |

## 7. Количественный анализ (дополнительно)
**Моделирование Монте-Карло** (10 000 прогонов, риски независимы, вероятности P из реестра): в среднем наступит **≈ 4,9 риска** за проект, в 90 % прогонов — не более 7. Поэтому реестр пересматривается на каждом Sprint Review, а резерв нужен не «на всякий случай», а обязательно.

![Монте-Карло](<06_схемы/Монте-Карло - NotaCode.png>)

## 8. Мониторинг
На каждом Sprint Review:
- проверяются триггеры;
- уточняются P и I;
- добавляются новые риски.

Ранние индикаторы — метрики потока (velocity, cycle time, WIP) для R1, R2 и R5. Главная работа критического пути ПЗ2 — 5.0 «Грамматика DSL» — связана с R3.

## 9. Выводы
- Идентифицировано 13 рисков шести категорий; оценка выполнена в шаблоне «Карта рисков».

- Преобладает стратегия снижения.
- Карта построена; реестр включён в Sprint Review.
