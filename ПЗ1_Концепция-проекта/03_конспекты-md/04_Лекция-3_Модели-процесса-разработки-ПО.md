## 1. Водопадная (каскадная) модель
Этапы: **1. Анализ требований → 2. Проектирование → 3. Разработка → 4. Тестирование → 5. Техническая поддержка.**

**Принципы:**
- этапы идут строго друг за другом;
- следующий этап начинается только после окончания предыдущего;
- возврат к пройденным этапам не предусмотрен;
- по каждому этапу создаётся полный комплект документации;
- качество оценивается по точности соответствия ТЗ.

Результат этапа — **продукт труда**, обычно документ. Типичный набор документов: спецификация требований; план проекта; проектные документы (архитектура, подсистемы, детальный проект); план тестирования и отчёт о результатах; описание конечной реализации; руководства администратора и пользователя.

| Достоинства | Недостатки |
|---|---|
| Устойчива к смене кадров | Неадаптивная структура ПО |
| Дисциплина исполнения | Игнорирует конечного пользователя |
| Гибкость на ранних этапах | Позднее тестирование |
| Ориентация на сроки и финансы | |

## 2. V-образная модель
Разновидность каскадной модели с упором на тестирование: каждому этапу проектирования соответствует свой этап тестирования.

| Левая ветвь (проектирование) | ↔ | Правая ветвь (тестирование) |
|---|---|---|
| Планирование проекта и требований | ↔ | Производство, эксплуатация и сопровождение |
| Анализ требований продукта и спецификаций | ↔ | Системное и приёмочное тестирование |
| Архитектурный проект на высшем уровне | ↔ | Интеграция и тестирование |
| Детализированная разработка проекта | ↔ | Модульное тестирование |
| | Кодирование (основание «V») | |

**Преимущества:**
- аттестация и верификация всех внешних и внутренних данных, а не только продукта;
- ход разработки удобно отслеживать по временной шкале, завершение фазы — контрольная точка;
- модель проста в использовании.

**Недостатки:** нет итераций между фазами; нельзя вносить динамические изменения требований; нет анализа рисков.

**Когда применять:** нужно тщательное тестирание (validation & verification); малые и средние проекты с чёткими фиксированными требованиями; есть квалифицированные инженеры, особенно тестировщики.

## 3. Модель прототипирования
Вместо «замораживания» требований до проектирования и кодирования создаётся **одноразовый прототип**, который помогает понять требования заказчика. Прототип тоже проектируют, кодируют и тестируют, но неформально и не тщательно. Заказчик «ощущает» систему, поэтому требования становятся стабильнее.

**Виды:**
- **эволюционное** — достоверность исходного образца постепенно повышается, пока он не станет законченной системой (анализ → прототип ⇄ оценка → конструирование → тестирование → релиз);
- **экстремальное** — для веб-приложений: статический HTML-прототип → DHTML-прототип → веб-сервисы → интеграция → релиз.

| Достоинства | Недостатки |
|---|---|
| Помогает выявить требования | Возможны высокая стоимость и сжатые сроки |
| Уменьшает риски | Поощряет «раздувание» требований |
| Конечная система стабильнее | Затрудняет поздние изменения требований |
| Пользователь взаимодействует с системой с ранних этапов | |

**Когда применять:** чтобы показать осуществимость нового подхода; при создании новых систем, когда неясны ограничения или алгоритмы.

## 4. Итеративная (инкрементальная, эволюционная) разработка
ПО создаётся пошагово: каждый шаг добавляет функциональность, пока система не будет готова. Первый шаг — простое начальное приложение с подмножеством ключевых, понятных и легко реализуемых задач, которое уже полезно.
Модель IID (iterative and incremental development; Т. Гилб, 70-е, «эволюционная модель»): каждая итерация — «мини-проект» со всеми процессами, итог — работающая версия. Реализована в RUP, MSF, XP.

**Фазы итерации:** начальное планирование → [планирование → требования → анализ и дизайн → осуществление → тестирование → оценка качества] (цикл) → внедрение.

**Преимущества:**
- серьёзные риски проявляются на ранних стадиях, поэтому их дешевле устранить;
- эффективная обратная связь с потребителем, продукт отвечает реальным потребностям;
- непрерывное итеративное тестирование;
- раннее обнаружение конфликтов между требованиями, моделями и реализацией;
- равномерная загрузка участников;
- реальная оценка состояния проекта, больше уверенности в успехе.

**Недостатки:**
- целостное понимание возможностей и ограничений долго отсутствует;
- часть сделанной работы приходится отбрасывать;
- снижается добросовестность («всё равно можно переделать позже»).

## 5. Спиральная модель
Предложена **Барри Боэмом** в середине 1980-х; основана на цикле Деминга **PDCA** (plan-do-check-act). ПО создаётся несколькими итерациями (витками спирали) методом прототипирования.
На каждом витке уточняются цели, оцениваются результаты, планируется следующая итерация. Оценивают:
- риск превышения сроков и стоимости;
- нужна ли ещё одна итерация;
- насколько полно и точно поняты требования;
- не пора ли прекратить проект.

**Схема спирали:** определение целей, альтернатив и ограничений → оценка альтернатив, выделение рисков и способов борьбы с ними (анализ рисков → прототип → рабочий прототип) → разработка и верификация очередной части продукта (концепция → требования → проектирование → кодирование → тестирование модулей → интеграция → приёмочное тестирование → развёртывание) → планирование следующих итераций. Ось — совокупная стоимость.

**10 главных рисков по Боэму (по приоритету):**
1. Дефицит специалистов
2. Нереалистичные сроки и бюджет
3. Реализация не той функциональности
4. Неправильный пользовательский интерфейс
5. Перфекционизм, ненужная оптимизация
6. Непрекращающийся поток изменений
7. Нехватка информации о внешних компонентах
8. Недостатки работ, выполняемых внешними ресурсами
9. Недостаточная производительность системы
10. Разрыв в квалификации специалистов разных областей

| Преимущества | Недостатки |
|---|---|
| Пользователи рано «видят» систему | Для малых проектов с низким риском модель дорога: анализ рисков на каждом витке стоит много |
| Пользователи участвуют в планировании, анализе рисков, разработке и оценке | Нужны высокопрофессиональные знания для оценки рисков |
| Гибкое проектирование | Спираль может продолжаться бесконечно: каждая реакция заказчика порождает новый цикл |
| Частая ранняя обратная связь, продукт высокого качества | Время на планирование, анализ рисков и прототипирование может оказаться чрезмерным |
| Не нужно заранее выделять все финансы | |

## 6. Agile
Процессная методология — серия подходов к разработке, ориентированных на итеративную разработку, динамическое формирование требований и их реализацию через постоянное взаимодействие внутри самоорганизующихся кросс-функциональных групп.

**Общие предпосылки:**
1. Переопределение ролей разработчиков, менеджеров и потребителей.
2. Отказ от «предваряющего анализа» (Big Upfront).
3. Итеративная разработка.
4. Ограниченная функциональность, основанная на договорённостях.
5. Фокус на качестве, достигаемом через тестирование.

**Организационные принципы:** клиент в центре; самоорганизация команды; устойчивый темп; минимально необходимое ПО (минимальная функциональность, только запрошенное, только код и тесты); допускать изменения.

**Технические принципы:** частые рабочие итерации; требования «замораживаются» на время итерации; тесты как ключевой ресурс (новая разработка не начинается, пока не прошли все тесты; сначала тесты); требования выражаются через сценарии.

**Ключевые роли:** команда (Team), владелец продукта (Product Owner), Scrum-мастер, потребитель (заказчик, пользователь).

**Ключевые практики:**
- организационные — ежедневные встречи (Daily), планирующий покер (Planning game), непрерывная интеграция (CI), ретроспектива, разделяемое владение кодом;
- технические — TDD, рефакторинг, парное программирование, простейшее работающее решение, стандарты кодирования.

**Артефакты:**
- виртуальные — use case / user story, график сгорания (Burndown chart);
- материальные — карточки историй (Story card), панель историй (Story board), открытая комната (Open room).

## 7. Scrum
Эмпирический, быстрый, адаптивный и самонастраивающийся подход к разработке. В отличие от водопада, построен на повторяющихся циклах, поэтому гибче и предсказуемее. Scrum позволяет разбить крупный проект на части и делать его постепенно, отклоняясь от пути, чтобы улучшить продукт.

**История (из заметок к слайдам):** Такеути и Нонака, статья «The New Product Development Game», HBR, 1986, «подход регби»; ДеГрейс и Шталь, 1991, впервые термин Scrum; Кен Швабер и Джефф Сазерленд, первая публичная презентация на OOPSLA’95; книга Швабера и Бидла «Agile Software Development with Scrum» (2001).

**Scrum крупным планом:** входы от заказчиков, команды, менеджеров и руководства → Product Owner → Product Backlog (приоритизированный список фич и багов) → Sprint Planning Meeting (команда берёт сверху столько, сколько может сделать к концу спринта) → Sprint Backlog (разбивка на задачи) → **спринт 1–4 недели** (дата окончания и объём не меняются) + ежедневный Daily Standup → Sprint Review → готовая работа → Sprint Retrospective.
**Три вопроса Daily:** что сделано с прошлой встречи? что будет сделано до следующей? что мешает?

**8 шагов Сазерленда** (книга «Scrum. Революционный метод управления проектами»):
1. Выберите владельца продукта — он знает цель и ожидаемый результат.
2. Соберите команду до 10 человек с нужными навыками.
3. Найдите скрам-мастера — он следит за ходом проекта и помогает бороться с трудностями.
4. Составьте бэклог продукта — приоритеты требований на Agile-доске (главная роль у владельца продукта).
5. Запланируйте спринты.
6. Проводите ежедневные 15-минутные митапы с тремя вопросами.
7. Проводите обзоры рабочих частей продукта со стейкхолдерами.
8. Проводите ретроспективу после каждого спринта; план изменений внедряйте в следующем спринте.

**Главные принципы Scrum (ценности Agile-манифеста):**
- люди и взаимодействие важнее процессов и инструментов;
- работающее ПО важнее исчерпывающей документации;
- сотрудничество с заказчиком важнее согласования контракта;
- готовность к изменениям важнее следования плану.

Scrum — «искусство возможного», девиз — следование здравому смыслу.

## 8. Сравнительный анализ

### «Тяжёлые» и «лёгкие» методологии

| Вес | Плюсы | Минусы |
|---|---|---|
| **Тяжёлые** | Рассчитаны на среднюю квалификацию исполнителей; большая специализация; ниже требования к стабильности команды; нет ограничений по объёму и сложности проектов | Нужна существенная управленческая надстройка; долгие стадии анализа и проектирования; формализованные коммуникации |
| **Лёгкие** | Меньше накладных расходов на управление проектом, рисками, изменениями и конфигурациями; упрощённые анализ и проектирование; упор на функциональность; совмещение ролей; неформальные коммуникации | Эффективность сильно зависит от людей; нужна квалифицированная, универсальная и стабильная команда; объём и сложность проектов ограничены |

### Выбор методологии по типу проекта

| Методология | Тип проекта |
|---|---|
| **Agile** | Стартапы, где нужно быстрее выпустить продукт и опередить конкурентов; проекты в новых технологиях, где результат нельзя предсказать |
| **Waterfall** | Системы жизнеобеспечения, где ошибка может быть фатальной |
| **V-model** | Продукты, работу которых нельзя остановить (например, ПО для авиации) |
| **RAD** | Проекты с короткими сроками |
| **Spiral** | Проекты с большими рисками, разработка военных объектов |
